# XY 业务简报

把已做的事、得到的结论和实际边界讲清楚，让不看实现细节的人也能据此沟通或决策。

## 表达方式

先用一句话回答核心问题。接着按需用 2～4 个短点说明：完成了什么、确认了什么、尚未完成什么、下一步需要谁决定。小任务可以只写一两句，不凑点数。

每点只讲一个事实或判断，优先说明对用户、交付或业务流程的影响。技术名词只有在影响判断时才保留，并用一句人话解释。区分“已经实现”“文档中有设计”“建议后续做”，不把推测写成事实。

提及外部文档时给出名称和可打开的地址；只有写入成功且复查过内容，才说“已写入”。提及未验证事项时说明具体边界，不堆泛泛的风险提示。

## 输出格式

默认采用纯文本排版：用“1、”“2、”或“已完成：”“结论：”分点。不要用 Markdown 列表符号、表格、加粗标记或代码围栏。段落之间留一空行；链接直接写地址。用户指定正式交付文件时，按其要求生成 DOCX 或 TXT，正文仍保持这种简短业务口径。

当角色层级、租户边界、模块归属或数据隔离用文字容易说绕时，优先使用 TXT 文本框结构图。文本框只使用实际空格、换行和 `├──`、`└──`、`│` 等字符保持层级；不要输出 `&#x20;` 这类 HTML 空格实体，不要改成 Markdown 表格。图只表达已确认的关系，不为了排版而补充未经确认的节点。

当内容是请求流转、服务调用、状态变化或带条件分支的流程时，可以使用 Mermaid 流程图。节点名称保持短小，先画主路径，再补必要的判断和异常分支；图后用一句话说明业务结论。能用两句话讲清的内容，不画图；不要同时画 TXT 图和 Mermaid 图来重复表达同一件事。
